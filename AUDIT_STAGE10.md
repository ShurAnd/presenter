# Presentator 2.4.1 — аудит тестирования, этап 10

**Исходная база:** рабочие исходники этапа 9 и архив HTML-покрытия `presentator-coverage(7).zip`, 3 ноября 2026 года. Это анализ кода и отчёта, **не результат нового запуска на Windows**.

## 1. Что реально известно

- В исходниках обнаружено **371 определение теста**: 349 обычных `#[test]` и 22 `#[tokio::test]`. **21 помечен `ignored`**, остальные 350 рассчитаны на обычный запуск. Эти количества получены анализом атрибутов в исходниках; работоспособность этапа 10 на Windows ещё не подтверждена.
- Последний отчёт LLVM: **4724/7659 = 61,68% строк**, **675/1069 = 63,14% функций**, **10443/16872 = 61,90% регионов**. В отчёте **нет измерений branch coverage (0/0)** — считать покрытие ветвей равным 61,68% нельзя.
- **Процент покрытия — только исполнение кода**: тест без сильных проверок способен покрыть строку, не заметив неверного поведения. Количество тестов тоже не является мерой качества.
- **Нет подтверждения работы с настоящим PowerPoint/COM, libmpv и аппаратными мониторами** только на основании unit-тестов. В частности, `ppt_flow_tests.rs` использует канал-подмену, а тесты `mpv.rs` подменяют таблицу вызовов C API.

## 2. Найденные риски: приоритет

| Приоритет | Находка | Доказательство / действие |
|---|---|---|
| **P1** | Сетевой загрузчик принимает блоки сверх объявленного `size` и записывает их до `UploadEnd`. | `src/net.rs`: ветка `Message::Binary` вызывает `write_all(&b)` без проверки `got + b.len() <= size`. Уже существует `known_issue_upload_must_not_exceed_declared_size_on_disk`, но он `ignored`. Нужна исправленная потоковая квота, затем включение теста в обычный прогон. |
| **P1** | Повторный `UploadBegin` во время текущей загрузки потенциально оставляет файл-сироту. | В `src/net.rs` новый `upload = Some(...)` заменяет старое состояние без удаления предыдущего временного файла. Добавить тест и согласованный способ обработки/очистки. |
| **P2** | Тест автозапуска восстанавливал только флаг существования, а не прежнюю строку реестра. | `src/watchdog.rs`: предыдущий `autostart_roundtrip` мог заменить пользовательскую строку. Этап 10: `Drop` возвращает **исходную строку** даже после паники теста. Запуск только по явному указанию на тестовой учётной записи. |
| **P2** | Тест реестра использовал фиксированное имя в `HKCU\Software`. | `src/registry.rs`: этап 10 использует уникальное значение и `Drop` для восстановления, проверяет также Unicode и перезапись. |
| **P2** | Тесты с `ignored` исключены из обычного прогона; часть требует живого стенда. | Инвентарь `TEST_INVENTORY_STAGE10.csv`; нельзя просто запускать `cargo test -- --ignored` на рабочем ПК: некоторые меняют автозапуск, отправляют команды серверу и используют документы. |
| **P2** | Отчёт не измеряет ветви. | Настроить отдельное измерение ветвей LLVM и последующую проверку влияния намеренно внесённых дефектов (mutation testing). Не интерпретировать нули как доказательство отсутствия ветвей. |

### Почему P1 важен

Это не теоретический пробел в графике: некорректный или повреждённый клиент способен заставить сервер временно записывать больше данных, чем ожидается. При сетевом доступе к Presentator это риск заполнения диска. Исправление рабочего кода **в данный архив не включено**, чтобы не менять протокол без отдельной проверки обратной совместимости.

## 5. Что реально добавлено в этом этапе

- **Три сетевых интеграционных теста с настоящим WebSocket на `127.0.0.1` и случайном порту:** отказ загрузки и восстановление на том же соединении; попытка выхода из рабочей папки через имя файла; отказ в загрузке при неправильном пароле. Содержимое проверяется чтением файлов с диска и событиями сервера.
- **Безопаснее реестровые проверки:** уникальное имя значения; восстановление прежних данных даже при панике; проверка записи Unicode. Опциональный автозапуск по-прежнему `ignored`, но теперь восстанавливает точную исходную строку.
- **Скрипт `scripts/verify_stage10.ps1`:** сохраняет список тестов, логи каждого прогона, версию Rust и (при наличии) состояние Git; никогда не запускает все `ignored` разом.

На Windows ожидается **374 определения тестов**, в обычном прогоне 353 и 21 ignored (371 + 3). Это **расчёт, а не подтверждённый успешный запуск**.

## 6. Критерии успеха дальше

1. Для каждого регрессионного риска есть воспроизводимый тест, который **падает при внедрении соответствующего дефекта** и проходит после исправления.
2. Тесты ясно разделены на: чистая логика, реальные локальные интеграции, ручные аппаратные/Office E2E. Моки не выдаются за проверки настоящего Office или видеодекодера.
3. Известные дефекты открыто перечислены и не маскируются статистикой. Особенно P1 загрузки файлов.
4. Проверять отдельно строки, функции, регионы, ветви и mutation score. **100% покрытия не гарантирует отсутствие дефектов**; недостижимые или платформенно-зависимые участки должны иметь документированное решение и интеграционный сценарий.
5. Сценарий запуска не должен сам изменять документы оператора, настройки запуска Windows и существующие процессы.

## Запуск

Распаковать заменяемые файлы в корень `C:\rust\presenter` поверх рабочего этапа 9 (файлы с относительными путями `src/...`, `scripts/...`). Затем:

```powershell
cargo test --all-targets stage10_ -- --nocapture
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify_stage10.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify_stage10.ps1 -Coverage
```

Нельзя запускать на рабочем стенде `cargo test -- --ignored`: некоторые тесты предназначены только для отдельного тестового пользователя/устройства. Тест известных дефектов сверхлимитной загрузки остаётся отключённым до исправления production-кода.

### Ограничение проверки

Исходные Rust-файлы и ZIP сверены, но в этой среде **нет `cargo`/`rustc` и Windows API**. Сборка, реальные тесты, новый процент и работа на пользовательском ПК не подтверждены. При ошибке на Windows нужен лог для исправления.
